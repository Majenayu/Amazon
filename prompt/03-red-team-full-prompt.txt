A. THE PROBLEM AND THE RULES
===============================================================================
Business Entity Resolution across three independent, noisy data sources.

Source 1 (S1) is a clean, already-deduplicated reference list of businesses. Sources 2
and 3 (S2, S3) are noisy fragments from other vendors. There is NO shared identifier.
The only usable fields are business_name and business_address, plus a country label.

Task: for every S1 entity, output the set of S2 and/or S3 records that refer to the same
real-world business. An S1 entity may match zero, one, or many records.

All files are TAB-separated .tsv. Addresses and the ID-list columns contain commas, so a
comma parse silently corrupts everything.

Source file columns (train_source1/2/3.tsv, test_source1/2/3.tsv):
  1. entity_id        — unique id; prefix S1- / S2- / S3- indicates the source
  2. business_name    — abbreviations, legal suffixes, typos, transliterations
  3. business_address — partial, reordered, missing components, landmark references
  4. country          — TRAIN covers {US, India}. TEST additionally contains France,
                        which has NO training labels. country must be treated as an
                        OPEN SET of string labels: it must not be hard-coded, filtered,
                        or one-hot encoded to {US, India}, and every test entity,
                        France included, must appear in the submission.

There is no separate source column; source is implied by the entity_id prefix.

Ground truth (train_ground_truth.tsv), two columns:
  1. source1_entity_id
  2. matched_entity_ids — comma-separated S2/S3 ids, EMPTY when the entity has no match

EVALUATION: macro-averaged F-beta with beta = 0.5, precision-weighted 2x over recall.

    F_0.5 = (1.25 * P * R) / (0.25 * P + R)

Computed PER S1 ENTITY, then averaged over ALL S1 entities in the evaluation set.
Singletons are included: an entity with no true matches scores 1.0 if an empty list is
predicted, and 0.0 if ANY match is predicted.

Algebraically, with m = true match count, k = predicted count, t = correct count:

    F_0.5 = 1.25t / (0.25m + k)                    for m > 0
    F_0.5 = 1                                      for m = 0 and k = 0
    F_0.5 = 0                                      for m = 0 and k > 0

Equivalently: F_0.5 = 1.25TP / (1.25TP + FP + 0.25FN).

Oracle form used below, where blocking retains r of an entity's m true matches and a
perfect matcher then selects exactly those r:

    O = 1.25r / (0.25m + r)                        for m > 0
    O = 1                                          for m = 0

Concrete sensitivity for an entity with 3 true matches: all 3 found with no false
positive = 1.000; all 3 found plus one false positive = 0.789; 2 of 3 found with no
false positive = 0.909. One false positive costs roughly 2.3x one missed link AT THAT
SET SIZE, but the ratio is set-size dependent, not a fixed cost.

Reference floor: predicting an empty list for every entity scores 0.0558 on train.

OUTPUT FORMAT. Two TSV files, both in output/ of the final zip:
  output/matching_results.tsv   — the ONLY file scored on the leaderboard
    columns: source1_entity_id \t matched_entity_ids
  output/candidate_pairs.tsv    — the candidate set actually fed into the matching model
    at inference time; the LAST blocking stage, not an early pass. Not scored, but
    audited for blocking quality (recall ceiling, reduction ratio).
    columns: source1_entity_id \t candidate_entity_ids

E. THE PLAN TO BE AUDITED
===============================================================================
Every decision is numbered. Attack decisions by number.

--- CORE THESIS ---
T1. Because each target has exactly one owner (C.1), the natural formulation is
    approximately 9.97 M target-side decisions ("which S1 owns me, or nobody"), not
    1.73 M entity-side searches.
T2. Therefore REVERSE retrieval (target -> S1) is the primary candidate generator, and
    forward retrieval (S1 -> target) demotes to a rescue channel.
T3. The score is won in the decision layer, not the matcher. Cosine already separates
    true from false pairs at 0.938 vs 0.177 (C.9); the loss lives in how many candidates
    are accepted, and in when none are accepted.

--- S0 INSTRUMENTATION ---
S0.1 Exact macro-F_0.5 scorer including singletons, built before any modelling.
S0.2 All blocking evaluated by ORACLE MACRO F_0.5, never micro link recall, because
     under a macro metric an entity with one true match that is missed loses a full 1.0
     while an entity losing one of six loses only 0.038.
S0.3 Fast panel of 25,000 S1 entities, stratified by country, match count,
     empty-address, native-script, and name rarity.
S0.4 Development holdout of 100,000 S1 entities plus a sealed 40,000 for final
     confirmation. Split by S1 entity, with all of an entity's targets kept together.
S0.5 Retrieval during validation always searches the full 10,320,219-target corpus, so
     that recall and ownership competition are not artificially inflated.

--- S1 NORMALISATION ---
S1.1 Three parallel views per record: raw, folded, variants. No single canonical string.
S1.2 Accent folding applied to LATIN SCRIPT ONLY. Indic combining marks are vowels and
     must be preserved.
S1.3 No discriminative token is deleted. Tokens such as center/service/group/partners
     are downweighted by IDF rather than removed, because of the 48.25% name-collision
     rate in C.4.
S1.4 Numeric view strips leading zeros but retains qualifiers (458-A, Bis, ter, 1/2).
S1.5 Trade-name wrappers split on dba / t/a / f/k/a / a/k/a, with BOTH sides retained as
     name hypotheses.
S1.6 Domains and handles decomposed into tokens.
S1.7 Address treated as an unordered bag of comma-separated components.
S1.8 State maps, street-abbreviation maps, city aliases and the France
     departement -> region map derived only from in-file co-occurrence, with support
     counts logged for the code audit.

--- S2 RETRIEVAL ---
S2.1 Channel A, primary: reverse retrieval. Index 1.73 M S1 records per country, query
     all 9.97 M targets, keep top-5 candidate owners per target. Approximately 49.8 M
     edges.
S2.2 Reverse rank used directly as an ownership feature.
S2.3 Channel B, rescue: forward retrieval, run only for S1 entities that received few or
     weak reverse-inbound edges. Separate address-token top-20 and name-token top-20
     indices.
S2.4 Channel C: name-only retrieval for the 4.39% of targets with empty addresses, gated
     on name rarity, skipped when all name tokens are common.
S2.5 Channel D: house-number + rare-street-token key, retained for its measured unique
     contribution in C.8.
S2.6 Candidate budget allocated by risk: more candidates for entities whose oracle loss
     would be total, that is, those with one or two true matches.

--- S3 MATCHING ---
S3.1 Two LightGBM specialists, one for S2 targets and one for S3 targets, justified by
     the divergent address-Jaccard profiles in C.3 (88.38% vs 68.79%).
S3.2 Negatives drawn only from retrieval output; random negatives capped at 5%.
S3.3 Country encoded as a categorical feature and never used as a filter, so that an
     unseen label cannot break inference.
S3.4 Pair features: per-field Jaccard / containment / Dice; char 3- and 4-gram cosine;
     rapidfuzz token_set and partial ratios; numeric agreement and contradiction;
     canonicalised state agreement; script flag; empty-address flag.
S3.5 Rarity features: maximum IDF of shared tokens, count of shared rare tokens, name
     frequency within S1.
S3.6 S1 SELF-AMBIGUITY feature: distance from this S1 record to its nearest OTHER S1
     record, computed once per country over all 1.73 M S1 records.
S3.7 Retrieval features: forward rank, reverse rank, generating channel, and
     forward/reverse agreement.

S3.9 TARGET-SIDE OWNERSHIP MARGIN: the gap between this S1 and the target's next-best

S4.1 A separate ENTITY-LEVEL singleton classifier rather than a score threshold.

S4.3 TWO-PASS OWNERSHIP: score, provisionally assign each target to its best S1,

F. WEAKNESSES I ALREADY SUSPECT
===============================================================================
Confirm, refute, or sharpen each of these, then find the ones I have missed. The value
of your report is mostly in what lies OUTSIDE this list.

W1. S2.1 / T2 coverage hole. Reverse top-5 gives no per-S1 coverage guarantee. Forward
    top-30 guarantees 30 candidates per entity; reverse retrieval may leave some S1
    entities with zero inbound edges. Under oracle macro, an entity with one true match
    and zero retained candidates scores 0, so reverse-primary may fail hardest on
    exactly the entities the metric weights most heavily. Is reverse-primary therefore
    wrong, or does it merely need a coverage floor?

W2. S4.6 / S5.2 direction error. The 1.230x shift in C.2 is in targets per reference. It
    is consistent with MORE DISTRACTORS or with MORE MATCHES PER ENTITY. I assumed
    distractors and concluded thresholds should rise. If the true cause is more matches
    per entity, raising thresholds is exactly backwards. Can the two causes be
    distinguished using only the provided files? If not, what is the minimax decision?

W3. S5.1 circularity. Removing references simulates added distractors only. Tuning
    thresholds in that environment bakes in the very hypothesis W2 says is unproven.

W4. S4.1 label definition error. The singleton classifier predicts m = 0, but the
    decision that actually maximises score is "predict empty", which is optimal both
    when m = 0 AND when every retained candidate is wrong. Conflating those two events
    may be a modelling mistake. Should the target be m = 0, or "empty is the
    utility-maximising action"?

W5. S4.3 leakage. Second-pass features derive from first-pass provisional assignments.
    Unless those assignments are generated out of fold, the second-pass model trains on
    its own in-sample output. Specify the exact leakage path and the minimum correct
    protocol.

W6. S7.1 internal inconsistency. Micro recall at K=50 is 93.85% (C.9). Is oracle macro
    >= 0.99 at 40 candidates per S1 even attainable? Give the reasoning that bounds it,
    and if the target is unattainable, state what it realistically is under the training
    size distribution in C.1.

W7. S3.8 independence assumption. Cross-candidate corroboration presumes S2 and S3
    errors are independent. If both vendors derive from a shared upstream, agreement is
    correlated and the feature will be systematically over-trusted.

W8. S3.1 data fragmentation. Two specialists halve the training data per model. A single
    model with a source-indicator feature may capture the same difference. What evidence
    would justify the split, and is the divergent address-Jaccard profile sufficient
    grounds on its own?

W9. S4.2 degeneracy. A relative margin is undefined or harmful when the entity's best
    score is itself low, and may over-accept on entities whose six true matches have a
    wide internal score spread. What guards are required?

W10. S2.6 unknowability. Budget is allocated according to whether an entity has one or
     two true matches, which is precisely what is unknown before matching. Is there a
     legitimate observable proxy, or is this rule circular?

W11. S2.4 guaranteed zeros. Skipping empty-address targets whose name tokens are all
     common guarantees a score of 0 for any affected entity that had exactly one match.
     Is that trade defensible under macro F_0.5?

W12. S3.6 unbudgeted cost. The S1 self-ambiguity feature requires an all-pairs
     nearest-neighbour search over 1.73 M S1 records per country, which is a second full
     retrieval job not accounted for in the S7.3 schedule.
